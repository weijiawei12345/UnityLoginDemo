# Docs 工作约定

此文件适用于 `E:\GameProject\ARPG\Docs` 及其子目录。

## 目标

- 保持文档与仓库真实状态一致。
- 用尽可能少的流程完成高质量文档工作。
- 优先减少 token、时间和重复劳动。

## 默认工作方式

- 默认采用轻量模式：先读现有文档和相关源码，再直接修改。
- 小改动不做完整规划、不做长篇 brainstorm、不做多轮形式化评审。
- 只在以下情况启用更重的流程：
  - 设计决策有明显分歧
  - 需要跨多个文件统一口径
  - 需要对外发布的正式方案/评审/规范
  - 文档内容高度依赖代码事实，且容易出错

## 具体原则

- 先看上下文：优先读取本目录已有文档，以及能证明事实的代码或配置。
- 只写有依据的内容：路径、类名、状态、约束、结论都要能追溯。
- 保持短句和直接表达，避免空话、泛化总结和过度修饰。
- 如果能用一句话说清楚，就不要扩成一段。
- 如果只需要修正一处措辞、补一个链接、改一个标题，直接改，不升级流程。

## 什么时候需要更谨慎

遇到下面内容时，先核对事实再写：

- 认证、联机、存储、权限、数据一致性
- 架构边界、状态机、生命周期
- 结论性表述，例如“已支持”“已保证”“不会发生”

## 风格约束

- 保持与本目录现有文档一致的术语，尤其是 Auth / Firestore / Fusion 相关名词。
- 优先使用明确的文件路径、类名和行为描述。
- 不要凭印象补全实现细节；不确定就标为待确认。

## 交付要求

- 修改文档后，简要说明改了什么、依据是什么、还有哪些未确认点。
- 如果引用了代码或配置，尽量给出具体路径。
- 如果发现文档与代码不一致，优先修正文档或明确标注差异。

## 推荐的轻量策略

- 默认使用较低成本的推理/模型配置。
- 只有在复杂争议、跨文件一致性、或最终定稿时才升级到更高成本配置。
- 能单次完成的，不拆成多轮工作流。
